# Results and artifact status

## Historical Phase 5 runtime fields

`phase5_final_evaluation.json` and `phase5_window_predictions.csv` are preserved
as the original Phase 5 protocol v1.1.0 artifacts. Their fixed-low and fixed-high
`avg_runtime_ms` values of `0.0` are placeholders, and the adaptive runtime fields
were measured with a different per-call method. None of those values should be
used for runtime comparisons.

The corrected four-method desktop runtime comparison is
`benchmark_fair_evaluation.json` with its per-window timings in
`benchmark_fair_windows.csv`. It uses the same 5 warmups and 25 timed repetitions
with `time.perf_counter_ns()` for fixed-low, fixed-high, Candidate v1.1, and
historical Adaptive v1.0. These measurements describe Python execution on the
host only; they are not firmware timing or physical energy measurements.

The Phase 5 runner no longer emits fabricated runtime values. Runtime comparison
belongs to the separate benchmark artifact; Phase 5 remains a frozen quality and
operation-count evaluation.

## Future Phase 5 artifact schema

The existing `phase5_final_evaluation.json` and `phase5_window_predictions.csv`
remain historical Protocol 1.1.0 outputs and are not regenerated by this change.
Future invocations of the Phase 5 runner write schema 2.0 to
`phase5_final_evaluation_v2.json` and `phase5_window_predictions_v2.csv`; the
runner refuses to overwrite either versioned output. The v2 prediction table
adds the adaptive v1.0 and Candidate v1.1 frequency estimates, allowing all four
methods' frequency MAEs to be reconstructed from the per-window records.

Frequency MAE eligibility is defined by a nonblank `target_frequency_hz`
(`normal` and `frequency_shift` windows; 160 of 320 windows in the frozen Phase 5
design). Multi-tone `added_harmonic` and transient `impact` windows are
ineligible. A missing or non-finite prediction on an eligible row now fails the
evaluation instead of silently reducing the denominator. New summaries record
eligible, scored, and missing-prediction counts per method.

New summaries also record the best-effort Git commit, working-tree dirty status,
Python version/implementation/platform, and NumPy version. If Git metadata cannot
be queried, the revision/status is explicitly `unavailable` with the error; this
does not retroactively establish provenance for historical results. Before
evaluation, the runner asserts development and held-out source-group IDs are
disjoint, in addition to checking existing split counts and the held-out hash.
